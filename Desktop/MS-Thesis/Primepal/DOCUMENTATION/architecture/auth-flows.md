# Authentication Flows

PrimePal uses two completely separate authentication systems. Never mix them.

## Teacher Auth (Supabase GoTrue)

```
Teacher → POST supabase.auth.signInWithPassword({ email, password })
       → Receives Supabase JWT (managed by GoTrue)
       → Frontend stores via supabase-js session management
       → Backend validates via supabase.auth.get_user(token) in get_current_teacher()
```

- **Frontend helper:** `lib/teacherAuth.ts` → `getTeacherHeaders()` reads Supabase session token
- **Backend dependency:** `app/core/security.py` → `get_current_teacher()` validates GoTrue JWT
- **Token location:** Managed by `@supabase/supabase-js` (cookie/localStorage)

## Student Auth (Custom PyJWT)

```
Student → Enters class code → GET /auth/classroom/{code}/avatars
       → Selects avatar → Enters 4-digit PIN
       → POST /auth/student/login { classroom_id, student_id, secret_pin }
       → Backend validates PIN, issues custom HS256 JWT
       → Frontend stores as localStorage['primepal_student_token']
       → Subsequent requests: Authorization: Bearer <custom_jwt>
```

- **Backend:** `app/core/security.py` → `create_student_token()`, `decode_student_token()`, `get_current_student()`
- **JWT secret:** `STUDENT_JWT_SECRET` env var (separate from Supabase JWT secret)
- **Token expiry:** 24 hours (hardcoded in `security.py`)

## Admin Auth

- Uses Supabase GoTrue (same as teachers) + an `invite_code` during signup
- Invite codes are generated by existing admins via the admin panel
- Frontend checks admin status via JWT claims decoded client-side (`lib/adminAuth.ts`)

## Important Notes

- Teacher and student tokens are **completely separate systems** — different signing secrets, different validation paths
- All teacher/admin endpoints use `get_current_teacher()` dependency
- All student endpoints use `get_current_student()` dependency
- The `get_current_student()` dependency reads from `Authorization: Bearer` header and decodes with `STUDENT_JWT_SECRET`
